领取所有奖励：四类渠道，一次点完，跑几步看得见

设计目标：一次点击按固定顺序领完四类奖励，并让「跑到第几步、到账多少、哪一步失败」全程可见。 三条硬规则决定这一页的形态：顺序固定且可见；到账数只认游戏回应，不按提交条数；任一步失败立即停下并如实报错， 绝不把前半段成功包装成「全部完成」。

03 · Channels

四类奖励：判定与重试各不相同

四类渠道的数据结构差异很大，领取逻辑必须按渠道分别定义，不能统一成「提交即到账」。

四类奖励动作

范围 / 可领判定 / 失败与重试

4 渠道
渠道范围可领判定失败与重试
使命 一般 412 · 每日 86 · 每週 24 · 活动 589 · 公会 92，合计 1,203，共用一张表 状态为「已完成」的行；一次提交全部可领 id 整批被拒时按 256 条分块重试；坏 id 只毁掉它所在块，其余照领，被拒块如实报出
礼物盒 表中每一行都可领，没有「已领」标记 表中存在行即可提交；无行则「本版本无内容」 领取后按返回的剩余表算到账（提交数 − 剩余行数），剩余为 0 表示已领完
赛季奖励 每轮提交「id × N 次」；服务端按 min(次数, 剩余可领) 封顶 每轮后重拉表，比对已领数量 被截顶的 id 下一轮次数翻倍，直到不再增长或到轮数上限；无增长如实写「当前没有可领取的赛季奖励」
活动角色奖励 服务端按「角色类型 + 进度」判定，客户端拿不到这两个值 用最保守参数发一次，比较前后「已领取」行数 无变化显示「本版本无内容」，不假装领到
顺序（固定） 使命 → 礼物盒 → 赛季 → 活动角色；任一步失败立即停止并报错。

四类渠道的「到账」都从游戏回应里算：提交成功不等于到账，这是本页所有数字的唯一来源。
